# Phase 1.5 — Parser enrichment design

Date: 2026-07-12
Status: Approved

## Context

Phase 1 (merged to master) extracts only ~4 of ~26 order-level fields and 3 of 14
item-level fields already present in the real OC detail payload (see
`docs/research/2026-07-12-parser-improvement.md` and
`docs/api/ordenes-de-compra-schema.md`). Three gaps matter enough to fix before Phase 2
(basket/baseline) and Phase 3 (matching/scoring) build on top of this data:

1. Cancelled orders are currently indistinguishable from completed ones — a correctness
   bug, since a cancelled order has no real transaction behind its price.
2. Currency/tax fields are not captured — orders can be denominated in CLP, UF, UTM,
   USD, or EUR and are usually net-of-IVA, so comparing raw `PrecioNeto` across orders
   without this context silently mixes incompatible values.
3. Line items carry only a free-text product name — no UNSPSC category/product code,
   which is the strong, language-independent join key Phase 2/3 basket matching needs.

All field names below are verified directly against the real captured fixture
(`tests/fixtures/oc_detail_sample.json`), not guessed or taken solely from the official
PDF data dictionary.

## Decisions

### A. Order status/type — drop cancelled orders

- Extract on every order (no filtering inside the parser): `CodigoEstado` (int, fixture
  shows `6`), `Estado` (str, `"Aceptada"`), `CodigoTipo` (str — fixture shows `"8"`, a
  JSON string, not an int), `Tipo` (str, `"SE"`), `CodigoEstadoProveedor` (int),
  `EstadoProveedor` (str).
- Only one status value is used as an active filtering criterion:
  `CodigoEstado == 9` ("Cancelada"), sourced from the official status table at
  `https://www.chilecompra.cl/api/`. The table's other seven values (4, 5, 6, 12, 13,
  14, 15) are extracted and stored, but the codebase does not currently rely on their
  exact meaning beyond the one fixture-confirmed example (6 = "Aceptada") — we do not
  invent behavior around unconfirmed codes.
- The table has no distinct "Rechazada" order-level state. Supplier-side rejection
  appears to live in `CodigoEstadoProveedor`/`EstadoProveedor` instead, but there is no
  real fixture example of a rejected order to confirm a mapping against. Decision:
  extract `CodigoEstadoProveedor`/`EstadoProveedor` now, but do not filter on them yet.
  Documented as an open question in `docs/api/ordenes-de-compra-schema.md` for future
  confirmation once a rejected-order payload is captured.
- Filtering location: `parser.parse_detail` keeps parsing every order, including
  cancelled ones, so "what fraction of orders get cancelled per buyer" remains an
  analyzable signal later and the parser stays a pure, total function (matching its
  current convention — no I/O, no policy decisions). A new module,
  `order_status.py`, exports `drop_cancelled(orders) -> list[PurchaseOrder]`, mirroring
  the shape of the existing `municipal.filter_municipal`. `ingest.run` calls it right
  before `store.orders_to_items_df`, alongside the existing municipal filter.

### B. Currency and tax — extract raw values only, no CLP conversion this phase

- Order-level: `TipoMoneda` (str, `"CLP"`), `PorcentajeIva` (float, `19.0`), `Total`
  (float), `TotalNeto` (float), `Impuestos` (float), `Cargos` (float), `Descuentos`
  (float).
- Item-level: `Moneda` (str, `"CLP"`), `Total` (float), `TotalCargos` (float),
  `TotalDescuentos` (float), `TotalImpuestos` (float) — alongside the existing
  `PrecioNeto`/`Cantidad`.
- No currency-conversion logic and no network calls in this phase. Converting UTM/UF/
  USD/EUR amounts to CLP needs an external, date-anchored rate source (research
  identifies `mindicador.cl` as the practical option) and a local rate cache — real
  design work that belongs in its own module once Phase 2/3 actually needs
  CLP-comparable prices for anomaly scoring, not before. Recorded as an ADR (see below)
  since it's a real architectural decision with alternatives, not just a task deferral.
- Rationale: keeps `parser.py` free of network I/O (matching its current pure-function
  convention) and avoids building rate-caching/staleness logic before it is
  load-bearing. All raw values needed to convert later (currency code, tax rate, net
  and gross totals) are captured now, so no re-parsing is needed when conversion is
  eventually implemented.

### C. Product classification — UNSPSC codes on line items

- Item-level: `Categoria` (str, human-readable category), `CodigoCategoria` (int,
  UNSPSC class-level code, e.g. `53111600`), `CodigoProducto` (int, UNSPSC
  commodity-level code, e.g. `53111601`).
- No UNSPSC lookup table, no basket-matching logic — that's Phase 2/3 scope. This
  phase only captures the codes faithfully so they're available when that logic is
  built.

## Data model changes

`models.PurchaseOrder` gains: `codigo_estado: int`, `estado: str`, `codigo_tipo: str`,
`tipo: str`, `codigo_estado_proveedor: int`, `estado_proveedor: str`,
`tipo_moneda: str`, `porcentaje_iva: float`, `total: float`, `total_neto: float`,
`impuestos: float`, `cargos: float`, `descuentos: float`.

`models.LineItem` gains: `moneda: str`, `total: float`, `total_cargos: float`,
`total_descuentos: float`, `total_impuestos: float`, `category: str`,
`category_code: int`, `product_code: int`.

All new numeric fields use the existing defensive `_to_float` coercion pattern (never
raise on a malformed value; default to 0.0/0 and let a later data-quality pass flag
outliers — out of scope for this phase per the research report's guardrails section,
which is not part of A/B/C).

## store.py (Parquet) changes

New order-level columns are flattened onto every item row (same pattern as the
existing `buyer_name`/`fecha` duplication), prefixed `order_` where the name would
otherwise collide with an item-level column of the same name:

`codigo_estado, estado, codigo_tipo, tipo, codigo_estado_proveedor, estado_proveedor,
tipo_moneda, porcentaje_iva, order_total, order_total_neto, impuestos, cargos,
descuentos`

New item-level columns: `moneda, total, total_cargos, total_descuentos,
total_impuestos, category, category_code, product_code`.

## Testing approach

TDD throughout, per project convention. Each new field gets a test asserting the
parsed value against the real fixture (`tests/fixtures/oc_detail_sample.json`), not a
synthetic dict. `drop_cancelled` gets unit tests with hand-built `PurchaseOrder`
instances covering both a cancelled and a non-cancelled order. `store.py` changes get
a test asserting the new columns appear with correct values in the output DataFrame.

## Out of scope for this phase

- CLP currency conversion (deferred; see ADR).
- Supplier identity (`Proveedor`/RUT) — research 2.4, not part of A/B/C.
- Unit of measure (`Unidad`) — research 2.6, not part of A/B/C.
- Extra order dates (`FechaEnvio`, etc.) — research 2.7, not part of A/B/C.
- Data-quality guardrails (negative values, Compra Ágil coverage gap) — research 2.10,
  not part of A/B/C.
- UNSPSC lookup table / basket-matching logic — Phase 2/3.
